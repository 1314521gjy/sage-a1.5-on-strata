# 8 GB 显存档：踩过的坑与读数口径（2026-10-22）

> 每一条都花掉过真实的测量轮次，按被咬的顺序记。**§1–§3 尤其重要。**

---

## §1 改配置后的第一条臂是脏的

同一条 argv，背靠背跑：

| 臂 | prefill | decode | CPU 池 |
|---|---|---|---|
| 冷盘首跑（GGUF 未进 page cache） | 247.7 | 52.14 | — |
| **同参数第二跑** | **939.4** | — | — |
| 换引擎后的第一条臂 | — | 44.15 | 10.459 ms/轮，16.7 GB/s |
| **同参数第二条臂** | — | **49.46** | **8.162 ms/轮，21.5 GB/s** |

**报第二条臂。** 上游 cyber-on-strata 的文档里也写着同一件事
（"切换配置后的第一条臂会被污染：43.15 vs 63.48 tok/s，池带宽 11.4 vs 22.5 GB/s"）。
拿第一条臂报数会把档位低估 10–20%，然后对着噪声做"优化"。

## §2 `copy ledger: prefill staging` **不是** MMQ staging

```
copy ledger: fill 2396 / 4351.59 MB; prefill staging 0 / 0.00 GB; swap 2006 / 3.56 GB
```

`prefill staging` 统计的是 **`pin_dmas()`**——pinned arena 的 DMA 计数，**不是** MMQ 的 `stage()`。
`stage()` 的计数只在 `ring2()` 打开时才打印（`T8 staging ledger` 那行）。

⇒ **`prefill staging 0` 不等于"prompt 走了纯 CPU"。** 设了 `STRATA_PIN_ARENA_GIB` 之后它是
`23532 / 13.91 GB`，不设是 `0 / 0.00 GB`。**只当它是指示器用。**
（这条曾让我连着四臂得出错误结论。）

## §3 短 prompt 不是廉价的测试

`prompt 8 tokens …` 看着像便宜的冒烟测试，但它什么都不代表：

- **`--expert-profile` 帮不上**——没有路由可排；
- 命中率塌到 **45%**，`CPU experts` 升到 **11–14 ms/token**（2002 token prompt 只有 0.6）；
- 少于 `--stage-ahead`（1024）token 时，批量 prefill 路径整个跳过。

**测速度用 ≥2048 token 的 prompt；短 prompt 只用来验正确性。**

---

## §4 解码三个独立的坑

1. **PowerShell 的 `1>` 写 UTF-16LE**，按 UTF-8 读得到 `'\ufffd\ufffd2\x003\x00'`，`int()` 当场炸。
2. **`vocab.json` 是 `{token: id}`，不是 `{id: token}`**——拿 id 去索引会拿到 `int`，报
   `'int' object is not iterable`。
3. **byte-level BPE 要过反向 byte 表**：先 GPT-2 byte↔unicode，再 UTF-8。

另外：`--tokens-file` 的输出是**一列 token id**，永远不是文本。引擎按设计不带 tokenizer。

## §5 池子过订阅是悬崖，不是斜坡

上游同机实测：

| workers | pool ms/轮 | decode |
|---|---|---|
| 0（默认＝所有可用线程，本机 **15**） | 3.470 / 3.528 | 83.21 / 82.00 |
| **6** | **3.118 / 3.111** | **88.73 / 88.66** ← 采用 |
| 8 + `--pool-affinity auto` | 3.070 / 3.792 | 90.09 / 85.31（单 rep，跨 rep 抖 0.72 ms，未采用） |
| **20** | **17.37** | **39.52** ← 2 倍物理核，5 倍悬崖 |

在 8P+8E 的片上，池子**在关键路径上**（验证器先等 GPU，再跑池，两者相加）。
留两个 P 核和全部 E 核给 host 循环，比多一个 worker 划算。**别超过物理核数。**

## §6 看着像省钱、其实不是的开关

| 开关 | 为什么不用 |
|---|---|
| `--kv-resident N` | 非驻留 cell 在核心里 `page=-1 ⇒ score=-FLT_MAX`，**静默丢上下文**。上游 20480 实测：21,385 token prompt 只读 18,432、**0 输出**。8GB 上这条必须保持 0 |
| `--pcie-frac F` | 在噪声底内（ABBA σ=4.13 tok/s vs 真差 0.67），且 `1.0` 更差 |
| `--expert-cache-per-layer` | 树内自报：**decoded 21% slower**（84.6 vs 106.6 中位） |
| `--prompt-batch` 低于 1024 | 低于约 1000 token 时**输出本身会变**（Q2_0 路径）。不做正确性 A/B 别调这个 |
| 借别的模型的 `pack` | pack 存的是**绝对字节偏移**（`native_experts.txt`: `0 12 13 0 1900544 …`）。换模型 ⇒ 偏移不同 ⇒ 静默读错张量 |

## §7 两个假警报，认得出来能省一轮

1. **"8K prompt 丢了指令。"** 没丢。`prompt_ids_8k.txt` 与 `prompt_ids_8k_task.txt` 差 80 字节，
   只有 `_task` 那份末尾带着 `\n\n请用中文总结上面这段文本的要点，分三条。`。
   用普通那份时，模型**继续** `问N→答` 的格式是**正确行为**。
   **先查 prompt，再怪引擎。**
2. **"流式档退化成自问自答。"** 32GB 全常驻档逐字复现同一段复读（`答：5050。问：…答：5050。`），
   是 `问：…答：` 的 prompt 形状，不是专家缓存。

还有一条**确实不适用**于本模型：上游那个 `idx_top_k` 预算 bug（2048 ⇒ 超过 2051 token 静默丢尾）。
本引擎线的 `qwen35` **没有 QSA 选择器**——`idx_top_k` 只出现在 `deepseek4` / `glm5next` 两个模型路径里。
8K prompt 实测整段都能答到，没有丢尾。

## §8 `<think>` 需要留够长度

Sage 是推理模型。`--max-new 64` 时 9 题里有 3 题还在 `<think>` 里、没出答案——只看尾巴会误判成"答不出来"。
32GB 全常驻档给 128 token **也仍然在想**。**给 ≥128，并且读完整输出。**
